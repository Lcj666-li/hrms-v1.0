## 1. 数据库设计（9 张表）

建表脚本 `hrms-backend/sql/init.sql`（MySQL 8，utf8mb4）：

| 表 | 用途 | SQLAlchemy 模型 |
| --- | --- | --- |
| `role` | 角色字典，仅 `employee` / `manager` 两种 | `app/models/role.py` |
| `department` | 部门，支持父子层级 | `app/models/department.py` |
| `position` | 岗位，关联部门 | `app/models/position.py` |
| `user` | 员工账号：工号、bcrypt 密码、部门岗位、直属主管 | `app/models/user.py` |
| `attendance` | 打卡记录（上班 / 下班），按人按日 | `app/models/attendance.py` |
| `leave_type` | 假期类型与额度规则（年假 / 病假 / 事假…） | `app/models/leave_type.py` |
| `leave_request` | 请假单：区间、状态、审批人、`leave_type_id` | `app/models/leave.py` |
| `salary_record` | 月薪条：应发 / 扣项 / 发放状态 | `app/models/salary.py` |
| `notice` | 公告 | `app/models/notice.py` |

- 早期版本没有假期类型与薪资两张表，`sql/migration_add_leave_type_salary.sql` 是给老库的
  增量脚本（新增两张表 + 给 `leave_request` 加 `leave_type_id`）。新库直接跑 `init.sql` 即可。
- 演示账号在 `init.sql` 尾部 seed（bcrypt 哈希写入，不是明文）。
- Agent 的 trace 存在**另一个库** `hrms_agent`，与业务库物理隔离（见第 3 节）。

## 2. 鉴权与角色

| 项 | 取值 | 位置 |
| --- | --- | --- |
| 算法 | HS256 | `hrms-backend/app/config.py` |
| 有效期 | `ACCESS_TOKEN_EXPIRE_MINUTES`，默认 1440（24 小时） | 同上 |
| 载荷 | `sub`（用户 id）、`role`、`name`、`exp` | `app/core/security.py` |
| 口令存储 | bcrypt | `app/core/security.py` |
| 角色来源 | 后端签发，Agent 侧只从 `/api/auth/me` 解析，**不接受请求体声明的角色** | `app/core/deps.py` · `hrms-agent/app/main.py` |
| 跨域 | `BACKEND_CORS_ORIGINS` 默认只放行 5173 的两个来源 | `app/config.py` · `app/main.py` |
| 限流 | 每用户 30 次/分钟，超限 429 + `Retry-After` | `app/main.py` · `hrms-agent/app/limits.py` |

连接层：SQLAlchemy 引擎开 `pool_pre_ping=True`、`pool_recycle=3600`，
避免 MySQL `wait_timeout` 之后拿到死连接报 "server has gone away"。

## 3. Agent trace 落库与运营面板

每轮问答写一条 trace 到独立库 `hrms_agent`（`app/store.py` 建表，`CREATE TABLE IF NOT EXISTS`）：

| 表 | 内容 |
| --- | --- |
| `agent_trace` | 会话、问题、角色、状态、planner、intent、token、总耗时、步数 |
| `agent_trace_step` | 每一步的工具、状态、耗时、参数、结果、错误 |

- **写入失败不阻断答题**：`store.save_trace` 捕获所有异常，只打印
  `[store] 写入 trace 失败` 后继续返回答案。
- **重复执行幂等**：同一 trace 再次写入前先 `DELETE` 旧步骤再批量插入。
- 历史 JSON 回填：`python scripts/backfill_traces.py`（重复执行安全）。
- 统计口径（`/agent/stats` 与面板 KPI 同源）：按天窗口统计总量、成功率、
  各状态分布、平均与 P95 延迟、token、planner 分布、工具 Top 及平均耗时。

## 4. 部署

```bash
cd hrms-agent
docker compose up -d --build
```

- 镜像基线 `python:3.11-slim`（`hrms-agent/Dockerfile`）。
- HRMS 后端跑在宿主机时，compose 通过 `extra_hosts` 提供 `host.docker.internal`；
  若两者进同一个 compose 网络，把 `HRMS_BASE_URL` 改成服务名即可。
- 后端与前端目前没有 Dockerfile，属已知缺口（见第 5 节）。

## 5. 已知短板

如实列出而不藏起来，这些也正是下一轮的迭代入口：

- **测试只覆盖 Agent**：`pytest` 33 个用例全在 `hrms-agent/`，
  业务后端（路由、权限、假期额度计算）与前端**没有测试用例**。
- **Agent 依赖清单缺一行**：`app/store.py` 与 `scripts/seed_demo_data.py` 用了 `pymysql`，
  但 `hrms-agent/requirements.txt` 没列，全新环境需要手动 `pip install PyMySQL`。
- **限流是单实例进程内滑动窗口**：多实例部署会各自计数，需要网关或 Redis 计数。
- **trace 存问题与答案原文**：含员工姓名、薪资区间等上下文，生产需要脱敏与保留期策略。
- **`hrms-agent/traces/` 未在 `.gitignore` 中**：审计与 trace 的 JSON 文件会进工作区，
  正式项目应排除或改落库。
- **端口与 CORS 硬编码**：8000 / 8010 / 5173 分散在 `config.py`、`vite.config.ts`、
  `src/api/agent.ts`，改端口要三处同步。
- **没有 HTTPS、找回密码、审计日志、组织架构变更历史**，定位是单机可跑通的原型。
- **制度问答是可选依赖**：知擎不在时 `search_policy` 只返回降级提示，
  Agent 不会退化成"用大模型常识回答公司制度"——这是刻意的取舍。

## 6. 扩展方向

- 后端与前端补测试（假期额度、薪资发放状态机、路由守卫），把 33 个用例的口径扩到全栈。
- trace 与审计统一进时序存储，接 Grafana 做 Agent 质量看板。
- 假期规则、额度、审批链做成可配置流程，替代写死的状态机。
- 引入 Redis 统一限流与幂等键，支持多实例。
- 与知擎之间从"HTTP 调用"升级为带超时预算与熔断的服务间调用，并把制度命中反馈回评测集。
